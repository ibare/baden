# Git 클라이언트 × Baden 연동 설계

> 상태: **제안 (미착수)** · 작성 2026-09-07

## 배경

AI 에이전트의 작업 현황을 빠르게 파악하려고 만든 Git 클라이언트가 따로 있다.
커밋 그래프와 변경 규모(파일 수, +/-), 파일 트리맵을 보여 준다.

문제는 이 뷰가 전부 **결과물 지표**라는 것이다. `22 files +1.3k −617` 은 무엇이
나왔는지는 말해 주지만, 그것을 만드는 데 무엇이 들었는지는 말해 주지 않는다.
Baden 은 그 반대편, 즉 **투입 지표**(이벤트 수, 소요 시간, 규칙 위반과 수정)를 갖고 있다.
둘을 커밋 단위로 이으면 Git 만으로는 보이지 않던 것이 보인다.

## 현재 데이터 구조

`events` 테이블 (`server/src/db/connection.ts:43`) 의 주요 컬럼:

```
id, timestamp, type, project_id, rule_id, severity, file, line,
message, detail, action, agent, step, duration_ms,
prompt, summary, result, task_id
```

**커밋 SHA 는 없다.** 커밋과 이을 수 있는 후보는 `task_id`, `timestamp`, `file` 셋뿐이다.

| 방식 | 정확도 | 문제 |
|---|---|---|
| 시각 구간 (이전 커밋 ~ 현재 커밋) | 낮음 | worktree 병렬 작업에서 즉시 깨진다. 같은 시간대 이벤트가 어느 브랜치 것인지 구분 불가 |
| `events.file` ∩ 커밋 변경 파일 | 중간 | 파일 단위 배지에는 충분. 커밋 단위 집계에는 부족 |
| **커밋 메시지 트레일러에 `task_id` 목록** | 높음 | rebase/squash 를 견딘다. 아래 설계의 축 |

SHA 를 키로 쓰는 매핑은 채택하지 않는다. `ff-develop` 워크플로가 rebase 를 상시
수행하므로 머지할 때마다 SHA 가 바뀌어 매핑이 전부 끊긴다. 트레일러는 커밋 메시지
안에 있으므로 rebase 후에도 따라간다.

## 서버 준비 상태

거의 다 되어 있다. 새로 만들 것은 엔드포인트 하나뿐이다.

- `server/src/routes/events.ts:62` — `taskId` 단건 필터 이미 존재
- `server/src/routes/analytics.ts:327-390` — task 단위 집계 이미 구현.
  `taskBreakdown` 이 `eventCount`, `violationCount`, `fixCount`, `fixRate`,
  `startedAt`/`completedAt` 을 그대로 내놓는다
- `task_id` 가 UUID 라 전역 유일 → 클라이언트가 리포·프로젝트를 몰라도 조회 가능

필요한 것: **`task_id` 배열을 받는 요약 엔드포인트** (`GET /api/tasks/summary?ids=a,b,c`).
기존 집계 로직 재사용이라 비용이 낮다.

## 연결 설계

### 1. 커밋 메시지 트레일러

커밋 하나가 여러 task 를 담을 수 있으므로 **목록**으로 둔다. squash 로 커밋이
합쳐질 때 트레일러도 자연히 합쳐진다.

```
Baden-Task: 846ecd94-9c5c-46ea-9c0f-8ba06b8d7c4e
Baden-Task: 1f2a...
```

### 2. 준수를 규칙에만 맡기지 않는다

`task_id` 는 세션 초반에 받는데 커밋은 한참 뒤에 한다. 컨텍스트가 압축되면
에이전트가 그냥 잊는다. **지시 따르기에 의존하는 데이터 파이프라인은 조용히 구멍이
나고, 구멍 난 것을 알아채기도 어렵다.** 결정론적 보강을 붙인다.

```
baden_start_task 응답 수신 → .git/baden-tasks 에 task_id append   (규칙)
prepare-commit-msg 훅      → 그 파일을 읽어 트레일러 삽입 후 비움   (자동)
```

이렇게 하면 에이전트는 `task_id` 를 **기억할 필요조차 없다.** append 한 번이 전부이고,
커밋 메시지 작성은 훅이 결정론적으로 처리한다. worktree 마다 `.git` 이 분리되어
있으므로 병렬 작업도 파일 단위로 자연히 갈린다. 규칙은 그 append 를 강제하는
용도로만 남는다.

훅이 Baden 서버에 직접 물어보는 방식("지금 활성 task 가 무엇인가")은 성립하지 않는다.
`baden_start_task` 가 `projectName` 만 받고 워크트리 경로를 받지 않으므로, 같은
프로젝트의 두 워크트리가 동시에 작업 중이면 서버가 구분하지 못한다. 파일 방식이
이 문제를 우회한다.

### 3. task ↔ 커밋은 N:M 이다

커밋 하나에 task 여럿(위의 목록)도 되지만, 반대로 **task 하나가 커밋 여럿에 걸친다.**
긴 작업을 세 번 나눠 커밋하면 그 task 의 이벤트 148 개가 세 커밋에 각각 148 로 찍힌다.
커밋 리스트에 "이벤트 148 / 위반 3" 을 그대로 얹으면 합계가 실제의 3 배가 되고,
"이 커밋의 노력"이라는 직관과 어긋난다.

**1 단계에서는 중복을 인정한다.** 지표를 "이 커밋의 노력"이 아니라 "이 커밋이 속한
작업"으로 프레이밍하면 오해가 없다.

**정확한 분할이 필요해지면 커밋 마커 이벤트를 도입한다.** 커밋 시점에 `task_id` 를
트레일러에 쓰는 그 순간 Baden 에 마커 이벤트를 하나 남기면,
`(task_id, 직전 마커 ~ 이번 마커)` 구간으로 이벤트가 정확히 분할된다.
SHA 를 쓰지 않으므로 rebase 에 안전하고, `task_id` 가 이미 브랜치를 구분해 주므로
worktree 병렬 문제도 자동으로 해결된다.

## 인사이트 후보 (가치 순)

1. **원 지시 ↔ 커밋** (`events.prompt`) — 가장 싸고 가장 유용하다. 커밋 메시지는
   AI 가 쓴 *결과 요약*이고 `prompt` 는 사람이 준 *의도*다. AI 작업을 리뷰할 때 실제로
   봐야 하는 것은 이 둘의 간극이다. 상세 패널 상단에 한 줄이면 된다. 집계도 통계도 불필요.

2. **노력 대비 산출** — 이벤트 수 ÷ 변경 라인 = 헤맴 지수. `+55 −1` 짜리 커밋에
   이벤트 140 개가 붙어 있다면 그것은 "사소한 수정"이 아니라 "원인 찾는 데 두 시간
   태운 지점"이고, Git 만 봐서는 영원히 보이지 않는다. 리스트 행에 얇은 막대 하나로 충분.

3. **작업 성격 분해** — `analytics.ts:751` 의 `Phase` 타입에 receive / plan /
   explore / rule_check / implement / verify / complete 분류가 이미 있고,
   `phaseTimeDistribution`(`analytics.ts:1268`)이 단계별 시간 분포까지 계산해 둔다.
   커밋별 비율을 스택바로 그리면 explore 비중이 높은 영역 = 코드를 이해하는 비용이
   비싼 영역 → 리팩터링·문서화 후보로 읽힌다.
   (주의: `action_prefixes` 의 category 는 별개 축이다. `verification` 은
   `rule_compliance` 로 흡수되었으므로(`connection.ts:293-303`) 그쪽을 근거로 쓰지 말 것.)

4. **검증 없는 커밋** — `verify` phase 이벤트(`classifyPhase`, `analytics.ts:760`
   에서 build/run/test/typecheck/verify/lint/validate 접두로 판정)가 0 인 커밋에 배지.
   단순하지만 신뢰도 신호로는 가장 강하다.

5. **위반 히트맵** — 트리맵이 이미 파일 단위이므로 `events.file` 로 조인해 위반 파일에
   배지를 겹친다. 트레일러 없이도 되는 유일한 항목이라 착수 부담이 낮다.

## 단계별 계획

| 단계 | 내용 | 비용 |
|---|---|---|
| 1 | `.git/baden-tasks` + `prepare-commit-msg` 훅 + append 규칙 신설 | 낮음 |
| 2 | `GET /api/tasks/summary?ids=` 엔드포인트 (기존 집계 재사용) | 낮음 |
| 3 | 클라이언트: 커밋 상세에 원 지시(`prompt`) + task 배지 | 낮음 |
| 4 | 커밋 마커 이벤트로 구간 분할 → 커밋별 정확 집계 | 중간, 데이터가 쌓인 뒤 |

1~3 까지가 실질적 가치의 대부분이다. 4 는 1~3 을 써 보면서 중복 집계가 실제로
거슬리는지 확인한 뒤에 결정한다.

## 리스크

- **커버리지 비대칭** — Baden 이 붙은 프로젝트만 데이터가 있다. 감시 대상이 아닌
  리포는 전부 빈 값이다. 새 컬럼이나 섹션을 상설로 두면 대부분의 리포에서 빈칸 뷰가
  된다. 있을 때만 얹히는 progressive enhancement 로 설계할 것.

- **이벤트 수는 자기보고다** — 에이전트가 얼마나 성실히 `baden_action` 을 불렀는지에
  좌우된다. 커밋 간 절대 비교는 위험하고 같은 세션 안에서의 상대 비교로만 읽어야 한다.
  "생산성 지표"로 오해되기 시작하면 숫자 자체가 오염된다.

- **데이터 접근 경로** — `~/.baden/baden.db` 가 WAL 모드라 외부 앱이 직접 열 때 락
  처리가 성가시다. 3800 서버가 상시 기동(`7d994d6`)이므로 HTTP API 를 1 순위로,
  미기동 시 read-only 직접 조회를 fallback 으로 둔다.
